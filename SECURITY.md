# Security Policy

## Supported versions

This project has not published its first public release. Until a signed release exists, no version is
designated as supported for security updates.

## Reporting a vulnerability

While this repository is private, there is no public reporting channel and none is needed: nobody
outside the owner can read the code.

Private Vulnerability Reporting is a public-repository feature, so it cannot be turned on in advance.
Enabling it is therefore a step of publication, not a precondition for it: the owner enables it under
**Settings → Security** in the same session that makes the repository public, and before the
repository is announced or linked anywhere. Publication is not finished until it is on.

Once enabled, use **Security → Report a vulnerability** in the GitHub repository so the report and any
proof of concept remain private. Do not open a public issue for an unpatched vulnerability.

Please include the affected version or commit, operating system, reproduction steps, security impact and
whether credentials or private source code may have been exposed. Do not include real credentials or other
people's personal data.

Maintainers should acknowledge a private report within 5 business days. Remediation and disclosure timing
depend on severity and on whether users need time to rotate credentials or update safely.

A published repository whose Private Vulnerability Reporting is off has an incomplete publication, not
merely a missing setting: this file is not a substitute for an operational private reporting channel.
Announcing or linking the repository before it is on is the thing to avoid, because that is the point
at which someone might have a vulnerability to report and nowhere private to send it.
