三件新手最常卡住的事

一、orchestrator 說找不到指令。先用完整路徑 "$HOME/.local/bin/orchestrator"；那不是安裝失敗，是這個目錄不在你的 PATH 裡。要不要改 shell 設定由你決定，安裝程序不會自己改。

二、什麼都還沒授權，所以什麼都會失敗。Workspace 白名單預設是空的， 沒有第 5 步，後面每一步都會被拒絕——這是刻意的，不是壞掉。

三、不要叫 agent 用 shell 指令進房。進房必須由它自己呼叫 room_join_request，系統才知道是哪一個活著的程序在申請。 shell 指令給不了這個資訊。

這個產品只在你自己的電腦上跑

GUI 只綁 127.0.0.1，也就是只有這台電腦自己連得到。沒有帳號、沒有雲端、沒有對外請求。 這份手冊不會教你把它開放給別台機器，那不是它的設計；要跨機器協作請等 docs/V2_ROADMAP.md 裡的 Remote Room Seat。

    03一個席位的一生

    席位（seat）＝一個活著的終端機程序。它不是帳號、不是模型名稱， 是「那一個正在跑的 Codex／Claude Code 程序」。點下面任一階段，看那個當下是什麼狀況。

    席位狀態機未申請
    最容易被跳過的一步

    「可以進來」和「可以被指派工作」是兩個不同的授權。 只做完 room_join_request 的席位會安靜地什麼都等不到——它在房間裡，但線路沒接上。

    04沒人在聽的時候

    這是整個系統最反直覺的一件事，也是最值得先弄懂的。 MCP 是一問一答的協定：伺服器只能回答客戶端正在問的問題， 沒辦法主動推東西給一個閒著的 agent。 所以一個席位只有在它自己開著 room_wait 的那段時間裡才叫得動。

    待命規則：room_wait 回來就要再叫一次

    不帶 timeoutMs 呼叫 room_wait，待命沒有時間上限：它會一直開著，直到某個可觀察的事件結束它—— stdio 關閉、你自己取消、Owner 撤銷待命、或心跳停止導致席位失效。這種情況下「掛著就好」是對的。

    傳 timeoutMs 才是有界等待，上限 4 小時。

    一個實際會踩到的坑：伺服器端確實沒有上限，但 Claude Code 的 MCP 工具閒置逾時是 1800 秒（30 分鐘）。 不帶 timeoutMs 的 room_wait 會在 30 分鐘被客戶端中止（錯誤訊息含 CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT）， 你以為它一直在待命，實際上 30 分鐘後就掉線了。實務做法：傳 timeoutMs: 1500000（25 分鐘）讓它乾淨返回，然後立刻再呼叫。 Codex／Grok 的客戶端上限依各家 CLI 而定，請自己量一次。

    不論哪一種，每次 room_wait 回來都要再叫一次才算持續待命：收到交辦回覆完、你傳的 timeoutMs 到了、 或是回 ROOM_WAIT_LEASE_LOST。同一個席位開新的 room_wait 會頂掉舊的，舊的回 ROOM_WAIT_LEASE_LOST， 這是預期行為不是失敗，繼續用新的那個就好。

    掉線的常見原因：終端回合結束、程序關閉，或自己傳了 timeoutMs 卻沒再叫。掉線之後席位就從「可交辦」掉回「不可即時喚醒」， 之後送來的工作沒有人接。

    交辦的 lease 規則（待推修正 675182b，推上去才成真）

    交辦送到席位、席位還沒回應之前有 60 秒；席位一旦回報「我收到了／我在做」（room_ack(read)／room_ack(working)）， 就沒有時間限制，做多久都可以。席位真的離開時，它手上的工作會自動回到佇列。

    為什麼這樣分：因為「送到了」是系統知道的事，「我在做」是 agent 自己說的，而它必須真的在執行才說得出口。

    lease token 原本同時是「所有權」與「期限」。修正後 ack 之後只拿掉期限，所有權仍在：token 仍證明這件工作是誰的， 別的席位拿不走，回覆也仍要帶它。不是「什麼都不管了」。

    誠實的代價：ack 過但永遠不回覆的交辦，現在沒有任何計時器會收回它，只剩席位被移除時才處理。 看到一筆 working 停很久，先去問那個終端，不要等系統替你判。

        ▤ 併入紀錄：四個區、四種顏色

        未進入併入 · 可重新發起藍。草稿版仍在等併入；可以勾選多筆「↻ 重新發起選取的核准」，會依 live main 重算預覽。同一個草稿版一次只能有一筆待答。
        未進入併入 · 不能重新發起灰。每一筆都寫明理由；這裡沒有按鈕是刻意的。
        兩個新的人工確認

        無法親自證實的紀錄。服務重新啟動過之後，它無法分辨一筆 promotion 是自己完成的、還是別的程式寫的， 因為紀錄、trace 與稽核檔都是同帳號可改寫的位元。這時「需要檢查」會出現一顆 「確認已檢查：我已自行檢查這個專案，沒有更早的併入還在執行」——在你按下之前，這個專案不會開始新的併入。 按下去不修復任何紀錄、不寫入 main，只記錄「你看過了」，而且重新啟動後會再問一次。

        釋放這筆等待。有些紀錄卡在「正在等某個程序結束」。「釋放」不會終止程序、不寫入 main、不代表併入已結束， 只表示你自己查看過那些編號；確認語逐字顯示在按鈕上方，按下即等於你說出那句話。

        一次性且綁死快照

        按上面那顆「草稿版又動了一次」看看：核准立刻失效。 草稿版 HEAD、你的專案 HEAD、路徑、預覽摘要——任何一個變了，就得重新預覽、重新問。 系統不會請你為你沒看過的內容簽名。

        為什麼要分類

        進場時系統會問你：接續房裡既有的工作，還是開始新任務？ 沒回答就直接用「起手類」工具動手，帳本會留一行 ⚠。那不是懲罰—— 房間裡可能已經有別人做到一半的事，這一行是讓後來讀紀錄的人不會把兩條線讀成一條。

        這份手冊描述的是 agent/native-full-trust-vnext 於 2026-09-05 的實際行為， 每一條規則都對照 public/room.html、public/room.js、src/mcp/collab-server.ts 與 docs/ 查證過。深入的逐項行為見 docs/RUNTIME_REFERENCE.md，威脅模型見 docs/THREAT_MODEL.md。

        草稿版不是作業系統層級的隔離保證。同一個帳號下的 full-trust agent 技術上仍可繞過應用層邊界。 它提供的是可追溯、可復原、有紀錄。需要強制的邊界請用容器或另一個帳號。
