# MCP 工具地圖：給進到房間裡的 Agent

## 這份文件補的是什麼

你呼叫任何工具時，MCP 協定**已經把那個工具自己的完整說明送給你了**——參數、錯誤碼、重試規則都在裡面。
那份說明是唯一的真相來源，本文件不重複它，也不會與它競爭。

你拿不到的是**這 27 個工具彼此的關係**：現在該用哪一個、下一步是什麼、哪些看起來像同一件事其實不是。
一個剛進房間的 agent 真正的困難不是「`room_send` 有哪些欄位」，而是「**我現在應該做什麼**」。

本文件只回答那個。

---

## 先建立心智模型

**兩個面，不能互相取代：**

| | 是什麼 | 用哪組工具 |
|---|---|---|
| **帳本** | 房間的共用記憶。只能往後追加、不能改寫，每個參與者都看得到 | `room_post` / `room_read` / `room_get` / `room_search` |
| **席位對話** | 你和另一個**活著的終端程序**之間的即時通訊 | `room_send` / `room_wait` / `room_reply` |

帳本不會叫醒任何人。席位對話會直接送到某一個確切的程序。
**把工作丟進帳本然後期待有人處理，是最常見的誤解——沒有人會被叫醒。**

**三種身分，不要混淆：**

- **常駐 worker**：`ask_codex` / `ask_claude` / `ask_grok` 叫起來的模型呼叫。**會花額度。**
- **終端席位**：像你一樣、活著的獨立程序。用 `room_send` 定址，**永遠不會被 worker 頂替**。
- **Owner**：那個人。他不在這些工具裡面——**他只出現在 GUI 和實體 TTY 上，那是你摸不到的地方。**

用 `list_agents` 分辨誰是誰。

## 標準流程

### 進場

```
room_init          → 取得（或開啟）這個工作區的房間。重複呼叫是安全的，回傳同一間。
room_join_request  → 請 Owner 允許你這個席位進來。他在 GUI 按。
room_wait          → 再請一次「待命」核准，然後開始等被指派的工作。
```

**`room_join_request` 和 `room_wait` 是兩個不同的授權。** 前者是「可以進來」，後者是「可以被指派工作」。
進來了不代表會被叫到；只呼叫前者的話，你會安靜地什麼都等不到。

**永遠不要用 shell 指令代替 `room_join_request`。** 系統必須知道是「哪一個活著的程序」在申請，
shell 指令給不了這個資訊。

### 被指派工作之後

```
room_ack(read)     → 立刻回報「我看到了」
room_ack(working)  → 回報「我開始做了」
room_reply / room_fail → 交出結果或說明失敗
room_wait          → 想繼續待命的話，再呼叫一次
```

`room_wait` 不是一勞永逸的。**每完成一件工作，想繼續待命就要再叫一次。**
那個私有的 lease token 絕對不要外流。

### 改程式碼

```
candidate_start     → 開一個獨立的分支與工作區。你的改動不會碰到主專案。
（工作）
candidate_checkpoint → 存一個可復原的快照。必須是已 commit 的乾淨狀態。
candidate_complete   → 完成，並取得預覽、測試、風險、復原點
```

`candidate_start` 會記下主專案當下的 HEAD，**並原地保留 Owner 未提交的修改**——
它不會 clean、stash、reset 或 merge 任何東西。

`candidate_checkpoint` 拒絕未提交的變更，是刻意的：**一個救不回來的快照沒有意義。**

### 請求 merge

```
main_merge_preview  → 從即時狀態重算 Owner 會看到的那個快照。不寫 ref、不 checkout、不改動任何被追蹤的檔案。
main_merge_request  → 登記一個問題。這不是核准。
```

**這裡是最多 agent 搞錯的地方：**

- **`main_merge_request` 不會 merge 任何東西**，也不會回傳任何你能用來執行 merge 的 token。
  它只是登記一個等 Owner 回答的問題。
- **只有 Owner 的 GUI 或實體 TTY 能核准**，一次只能用一次，而且綁死在那個快照上。
- 只要 candidate HEAD、主專案 HEAD、路徑或預覽摘要**任何一個變了，核准會被拒絕**，
  不會被悄悄指向新的內容。
- 預覽如果**顯示不完整**（檔案被截斷、或模擬合併有衝突），會回報 `approvable: false`。
  **不要想辦法繞過它**——那個旗標存在的意義，就是不讓 Owner 為他沒看過的東西簽名。
  正確的做法是**把變更拆小**，直到預覽裝得下。

**先 `main_merge_preview`、把結果給 Owner 看過，再 `main_merge_request`**，
並帶上剛拿到的 `previewDigest`。順序反過來的話，你是在請人簽一份他沒讀過的東西。

**「不改動任何被追蹤的檔案」不等於「完全沒有副作用」**：若該 repo 設定了 merge driver，
預覽會執行 **main 的那一份**（不是 candidate 的），而任意程式可能在 main 的工作目錄留下暫存檔。
這是為了讓預覽與實際 merge 執行同一支程式所付的代價，已記於 [[THREAT_MODEL]] F23。

## 錯誤處理：一條總規則

**任何工具說明裡沒有點名的錯誤，都不要盲目重試。先呼叫 `candidate_status` 弄清楚真實狀態。**

`candidate_status` 是這個房間的**唯一真相來源**：任務、checkpoint、核准紀錄、
candidate 與主專案的即時 HEAD、未提交狀態、復原是否就緒、以及**先前的完成預覽是不是已經過期**。

會改變狀態的工具都要求一個 **`clientRequestId`**（穩定的 UUID）：

- **同一個邏輯呼叫，每次重試都用完全相同的值。** 這樣傳輸層重試不會產生第二個成品。
- **同一個 key 配不同的輸入會直接失敗**，不會將錯就錯。

## 花額度的工具

`ask_codex`、`ask_claude`、`ask_grok`、`room_mention`、`compare_agents` **會實際呼叫模型。**

`room_post` **不會**。想留紀錄而不吵醒任何人的話用它——
它也會擋掉以 `@codex`、`@claude`、`@grok` 開頭的文字，要求你改用 `room_mention`，
因為那種寫法看起來像在叫人，實際上不會。

`request_coding_workflow` **只是排隊等 Owner 審**。它不核准、不啟動、不測試、不編輯、不花額度。
**待審的提案永遠不等於核准**，你也不能把它換成執行用的 nonce。

---

## 四件你做不到的事（這是設計，不是限制）

1. **你不能核准自己的 merge。** 能核准的介面在你摸不到的地方。
2. **你不能偽造寄件者身分。** 那是伺服器綁定的，不是你送出來的欄位。
3. **你不能把工作丟給常駐 worker 代替某個終端席位。** 定址到席位的訊息永遠不會 fallback。
4. **你不能繞過 `approvable: false`。** 那不是一道你該想辦法通過的檢查，
   而是一個「Owner 還沒看到全部內容」的事實陳述。

---

## 誠實聲明

candidate **不是** OS 強制沙箱。同一個作業系統帳號下、擁有完整主機能力的程序，
技術上仍然可以直接改主專案、停掉監控或刪掉備份。

Orchestratory 提供的是**可追溯的快照、明確的核准、以及復原優先的設計**，
不是對惡意程序的強制隔離。這份文件不會給你更好聽的說法。
